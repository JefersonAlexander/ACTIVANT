# Auditoría previa al despliegue — ACTIVANT

Fecha de trabajo: 13 de noviembre de 2026, America/Bogota. Los artefactos usan hora UTC y pueden indicar 14 de noviembre. Dictamen: **NO APTO todavía para uso institucional en producción**. El código dispone de controles locales comprobados; el entorno Supabase Cloud tiene bloqueos de configuración y esquema. No se publicaron servicios, no se aplicaron migraciones remotas y no se usaron datos de funcionarios.

## Alcance y método

Se revisaron rutas y módulos existentes, `AGENTS.md`, contratos de autenticación, migraciones SQL, funciones privilegiadas, políticas, configuración, pruebas y documentación. Se consultaron las guías de la versión instalada de Next.js para instrumentación, cabeceras y despliegue, y documentación oficial de Supabase enlazada en la [guía de despliegue](deployment.md).

Las comprobaciones SQL utilizan PostgreSQL 17.11 real descartable con roles y RLS reales, más contratos mínimos locales de Auth/Storage. No verifican los servicios gestionados. Playwright utiliza Chrome en escritorio y móvil emulado, SDK Supabase real y un doble HTTP/WebSocket con identidades sintéticas. La conexión Cloud se comprobó por separado, con clave publicable local, sin crear usuarios ni leer filas personales.

Los 220 checks SQL incluyen reservas simultáneas por último cupo, cancelaciones, ofertas y respuestas concurrentes, vencimiento/reasignación, duplicados, acceso ajeno/anónimo, puntos por evento, cambios de bono, revisión y compensaciones. Las pruebas nuevas de sanciones hacen rollback de sus fixtures; no alteran reglas temporales del código productivo ni manipulan bases externas.

Los 110 casos de navegador incluyen sesión expirada renovable/revocada, cookie manipulada, perfil desactivado, permisos administrativos, orígenes falsificados, callback, reservas, QR, puntos, espera y biblioteca. Se revisaron visualmente capturas del login móvil y dashboards de usuario móvil/administrador escritorio; las comprobaciones axe y desbordamiento de la suite no detectaron infracciones en los estados examinados.

PowerShell reportó código de wrapper 1 al redirigir stderr, pese al resumen Playwright aprobado y sus dos `.last-run.json` con `status: passed` y `failedTests: []`. Se reprodujo el comportamiento con un proceso Node sintético que escribe en stderr y termina con código nativo 0; al propagar explícitamente `$LASTEXITCODE`, el wrapper termina en 0. Es una limitación del wrapper de esta sesión, no un fallo de aserción oculto. Al guardar logs desde PowerShell, capturar y propagar el código nativo, en lugar de usar únicamente `$?`.

No ejecutados: integración autenticada completa con Supabase Cloud, pgTAP mediante CLI, SMTP real, planificador Cron alojado, Realtime alojado, prueba física de cámara, carga, escaneo DAST externo, backup/restauración remota, build Docker y ejecución de GitHub Actions. El workflow está preparado, pero un archivo YAML no demuestra una ejecución CI.

Los fallos de arranque/red de la sandbox se distinguieron de los resultados del aplicativo; los comandos necesarios se repitieron con autorización. El primer smoke detectó ausencia de HSTS al usar un build de desarrollo; se recompiló con perfil producción y el smoke pasó. Esa diferencia de build está documentada en el procedimiento.
